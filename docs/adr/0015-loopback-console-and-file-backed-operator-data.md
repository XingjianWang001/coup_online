# A loopback-only Console, and Operator data kept in local files

The Operator had no way to see the server. `docs/deployment.md` says to make sure no Game is in progress before an update, but nothing could tell whether one was, and there was no answer to "is anyone playing, and how?". The server now serves a read-only Console and keeps Game Summaries and Visits on disk.

**The Console listens on its own port, bound to the server's `127.0.0.1` and not proxied by Caddy.** The Operator reaches it through the SSH port forward that `deploy.cmd -AccessOnly` already opens, so the SSH key is the only credential and the server holds no login code. The Console serves a JSON endpoint and a page that polls it every 5 seconds. The deploy script reads the same endpoint over SSH before it restarts the app. If any Room has a Game in progress with a Human Player still in it, the script stops and asks the Operator whether to continue. It only warns about Lobby Phases and finished Games, and ignores Rooms where only Computer Players are still playing. A Game that starts in the seconds between that check and the restart is lost. The Console is read-only, so no maintenance mode exists to prevent that.

**The Console shows everything, Hidden Cards, Deck and Temperaments included.** The Operator is trusted with it. An Operator who also sits at a Table could therefore read the other Players' cards. This was accepted knowingly, and it is one more reason the endpoint must stay off the public network.

**Game Summaries and Visits are appended to JSONL files in a Docker volume.** Every Game that starts leaves one Game Summary, including Games that end early (a Rematch after every Human Player is out, or a Room emptied mid-Game). Those are marked as ended early, have no winner, and are left out of win rates. Game Summaries hold no personal information and are kept forever. Visits go into one file per day, and files older than 90 days are deleted whole. ADR 0003 still holds: Game state is not persisted, and a restart still loses the Rooms in play.

**A Visit stores where and when, never who.** The client IP is resolved to a region with ip2region at write time (city in mainland China, country elsewhere; the SSH tunnel and localhost count as local), then discarded. Neither the raw nor a truncated IP is written down. A Visit is recorded only for four events: opening the home page, creating a Room, joining one (through an Invite Link or by Room Code), and starting a Game. Its time is rounded to the hour, and it carries no nickname or Room Code. Unique Visitors are counted per day from an HMAC of the IP whose key changes daily and lives only in memory. Hashes from different days cannot be linked, not even by the Operator. Crawler and scanner traffic is counted as normal Visits.

**Considered Options**: SQLite through `node:sqlite` adds no dependency, but it is still experimental in Node 22, and an append-only file per day already answers every question the Console asks. A JSONL file can be imported into SQLite later if ad-hoc queries are needed. MaxMind GeoLite2 needs an account, a license key and a public attribution, and it is less accurate than ip2region for Chinese cities. Storing a truncated IP was rejected because the region is all it would be used for, and that is already resolved at write time. Province-level regions were offered and declined. Sharing the game port and reusing the loopback check of `canStartTunnel` was rejected because that trust boundary has been bypassed three times (#45).

**Consequences**: ip2region's data is bundled in the image and goes stale until the dependency is bumped. A restart replaces the HMAC key, so one Visitor who comes back on the day of a deploy counts twice. At city level and hourly precision, with a small circle of friends, the Operator can often guess who a Visit was. No notice of the Visit collection is shown to Players. That was the Operator's call, made knowing that processing an IP into a city may need one under PIPL. MISSION's "no database" constraint now reads as no database service. Operator data in local files is allowed.
